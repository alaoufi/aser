# تصميم منصة أكلات وغذاء الأجداد

الحالة: مقترح للمراجعة قبل التنفيذ. مصدر المتطلبات: مواصفات المستخدم الكاملة
المحفوظة في `docs/REQUIREMENTS.ar.md`. هذا المستند لا يعلن اكتمال أي وظيفة.

## الهدف والنطاق

منصة سعودية عربية للأسر المنتجة الغذائية فقط؛ تصفح دون تسجيل، واكتشاف الأسر
والمنتجات حسب الموقع والتصنيف، وتواصل مباشر، مع مراجعة إدارية قبل إتاحة البيع.
التسجيل مجاني، ولا عمولات أو اشتراكات أو دفع إلكتروني في الإصدار الأول.
الهوية الوطنية أداة مراجعة إدارية وليست ترخيصًا، والاستثناء لا يتجاوز أي ترخيص
إلزامي. علامة التوثيق قرار إداري موثق وليست اعتمادًا حكوميًا.

## البدائل

1. المقترح: Next.js وTypeScript للموقع والواجهات ولوحات التحكم وAPI تحت مشروع
   واحد، مع PostgreSQL الحالي. يقلل تكرار الشيفرة والتشغيل ويدعم صفحات عامة
   قابلة للفهرسة. توضع العمليات في خدمات مستقلة عن صفحات العرض لتستخدمها
   تطبيقات الهاتف لاحقًا عبر API.
2. واجهة React وخادم API مستقل: فصل أكبر للنشر والتوسع، مقابل خدمتين ودورة
   مصادقة وتشغيل أكثر تعقيدًا في مرحلة لا تحتاج ذلك بعد.

اختيار البديل الأول توصية تنفيذية ولم يُسجل بعد كقرار وافق عليه المستخدم.
تُحدد الإصدارات المدعومة والمكتبات بعد التحقق من الوثائق الرسمية وقت البناء.
التطبيقات الأصلية Android وiOS في المرحلة الثالثة، وليست نتيجة تلقائية لبناء الموقع.

## الواجهة المقترحة

- RTL على جميع الشاشات، واسم «أكلات وغذاء الأجداد» حسب المواصفات الأصلية.
- خلفية قمحية وألوان قهوة وتمور ولمسات أخضر زيتوني، وخط عربي واضح وأزرار كبيرة.
- الرئيسية: مقدمة مختصرة، بحث واختيار مدينة يدوي، الأقسام الـ12، الأسر المعتمدة
  والمنتجات الجديدة والمتوفرة وحسب الطلب، ودعوة التسجيل كأسرة.
- صفحات النتائج: مرشحات المنطقة والمدينة والتصنيف والتوفر وخيار الاستلام.
- صفحة الأسرة: تعريف وتوثيق وساعات عمل وتوصيل ومنتجات وأزرار التواصل والمشاركة.
  لا تظهر نقطة الاستلام الدقيقة في المرحلة الأولى؛ مشاركتها مرتبطة بطلب وموافقة
  الأسرة في المرحلة الثانية. الموقع العام والمدينة فقط متاحان علنًا.
- صفحة المنتج: صور وسعر محدد أو استفسار ومعلومات السلامة والحساسية والحفظ.
- حالات واضحة للتحميل والفراغ والخطأ؛ لا أسماء أسر أو تقييمات أو منتجات مختلقة
  في الإنتاج. تستخدم fixtures معزولة للاختبارات أو معاينة التصميم فقط.
- التسجيل متدرج: التحقق من الهاتف، الأهلية، بيانات الأسرة، الاستلام والتوصيل،
  ثم مراجعة الطلب؛ الموقع الدقيق والمستندات لا تظهر للعامة.

## البنية والبيانات

قاعدة jdatna الحالية وحدها، مع migrations مرقمة بحساب migrator وحساب runtime
محدود. لا اتصال إلى قاعدة أي خدمة. جداول المرحلة الأولى: المستخدمون والأدوار
والجلسات، الملفات التجارية والتحقق والمستندات والروابط، المناطق والمدن والأحياء،
التصنيفات والمنتجات وعلاقاتها ووسائطها وحساسيتها، نطاقات التوصيل ونقاط الاستلام
وساعات العمل، البلاغات وسجل التدقيق والإعدادات. تُضاف جداول الطلبات وما يتبعها
بترحيلات لاحقة، دون تشغيل واجهات طلبات غير مكتملة.

قيود فريدة للموقع وروابط التصنيفات ومفاتيح أجنبية وعزل ملكية الأسرة في كل عملية.
المنتج متعدد التصنيفات بسجل واحد، والسعر عند التواصل لا يصبح صفرًا أو زر دفع.
تنشر الأسر المعتمدة فقط، والوثائق وتغييرات التوثيق لها صلاحيات وتدقيق مستقلان.

تُخزن الوسائط في خدمة S3-compatible مستقلة تخص jdatna أو مزود يعتمد لاحقًا؛
لا تُحفظ ملفات المستندات داخل PostgreSQL أو في مسار ملفات عام. تشفير الملفات
الخاصة وروابط قصيرة العمر، وحدود حجم وأنواع مسموحة، وإزالة البيانات الوصفية
للصور عند الحاجة. اختيار مزود التخزين وOTP يعتمدان على الوصول والتكلفة الفعلية؛
لا شراء اشتراك ولا إرسال رسائل مدفوعة دون اعتماد. يمكن بناء واختبار adapters
محلية مع منع استخدامها للإنتاج أو اعتبارها تحققًا فعليًا من رقم الهاتف.

## المصادقة والصلاحيات

جلسات آمنة HttpOnly/Secure، وحماية CSRF وحدود محاولات التسجيل وOTP وتحقق المدخلات.
صلاحيات عميل وأسرة وإدارة مفصولة على الخادم، ولا يكفي إخفاء أزرار الواجهة.
الأسرة تدير منتجاتها وملفها فقط؛ الإدارة وحدها تراجع المستندات وتعتمد وتعلق مع
سبب وسجل. يُجهز حساب الإدارة الأول بإجراء آمن منفصل، دون كلمة مرور افتراضية.

## Coolify والنشر

حسب توجيه المستخدم، يُربط المشروع بـCoolify **بعد** تجهيز الموقع واختباره.
تُجهز Dockerfile وفحوص الصحة وبناء قابل للتكرار، ثم مورد مستقل باسم jdatna،
بأسراره وحدوده وشبكاته. لا يُسمح لـCoolify بإنشاء PostgreSQL بديل أو استيراد
قاعدة أي خدمة أو تغيير 80/443 على الخادم دون تصميم توجيه متوافق مع Caddy الموجود.

قبل النقل تُراجع إعدادات Coolify الحالية بقراءة فقط وتُحفظ نسخة وتُثبت استعادة
jdatna. يُحافظ على mount التخزين قبل تشغيل الحاويات، فلا يبدأ التطبيق أو DB
على المجلد الأساسي عند غياب loop mount. لا يكون هناك مديرَا تشغيل للحاوية نفسها:
Coolify يدير التطبيق فقط، وتبقى قاعدة PostgreSQL ووحدات التخزين تحت systemd.
تظل صفحة الإنشاء العامة حتى اجتياز فحوص القبول وجاهزية الخدمات الضرورية.
التسجيل الإنتاجي يبقى مغلقًا حتى اختبار OTP حقيقي وتخزين مستندات خاص وآمن؛
غيابهما لا يمنع بناء الواجهات والخدمات واختبارها محليًا.

## اختبارات القبول

- البناء وفحص TypeScript واختبارات الوظائف الحساسة والصلاحيات.
- اختبار تصفح RTL والجوال، البحث والمرشحات والصفحات الفارغة وإدخال نص عربي.
- تسجيل أسرة ومراجعتها ورفضها وتعليقها، وصلاحيات الملفات الخاصة ومنع تجاوز الملكية.
- إضافة منتج وتعديله وتصنيفاته، وحالات السعر والتوفر والتوصيل والروابط الآمنة.
- فحص الترحيلات والنسخ والاستعادة في jdatna فقط وعدم وجود بيانات اختبار في الإنتاج.
- بعد النشر: HTTPS والنطاقان وفحص الصحة، واستجابة أي خدمة وعدم تغيير قاعدة بياناته.

## حدود المراحل

المرحلة الثانية: طلبات المنصة والاستلام والتوصيل والإشعارات والمفضلة والتقييمات
الموثقة والطلب المسبق. المرحلة الثالثة: Android وiOS والعروض والإحصائيات والبحث
المحسن. لا يُعلن اكتمال مرحلة لمجرد نجاح تصميم الواجهة.

## ما يحتاجه التنفيذ لاحقًا

مزود OTP مناسب وتكلفته، ووجهة تخزين خاصة ونسخ خارج الخادم، وطريقة منح أول حساب
إدارة. تُطلب هذه المعلومات عند الحاجة لها، مع استمرار الأعمال المحلية المستقلة.
