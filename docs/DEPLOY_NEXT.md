# النشر القادم — جاهز للتنفيذ عند فتح اللابتوب

**لمن:** فزاع، أو أي وكيل لديه SSH إلى خادم جدتنا وصلاحية Coolify.
**الحالة:** كل الكود مدموج أو جاهز في GitHub، والاختبارات ناجحة. المطلوب جلسة واحدة على الخادم.

## ما يُنشر

آخر `codex/jdatna-platform` بعد دمج طلب الدمج #10. يتضمن:
- التصميم التراثي.
- تنبيه «لديك طلب جديد» للأسرة، ومراحل تنفيذ الطلب.
- مراجعة الطلب ورسالة التأكيد للعميل.
- البحث بأربع طرق: بالكلمة، والمتاح الآن، وحسب الأسرة، وحسب القسم.
- الترحيلان الجديدان `017_order_fulfillment.sql` و`018_admin_login_otp.sql`.
- إصلاحات الإدارة: دخول المدير برمز SMS، وملخص، وتبويب الطلبات، وتصفية الأسر.

الترحيل `017` إضافي ومتوافق مع الإصدار الحي `30b97ec`: يوسّع قيد الحالة، ويضيف عمود `producer_seen_at`، ويعلّم الطلبات القديمة كمطّلع عليها. لا يحذف بيانات.

**مهم لدخول الإدارة بعد النشر:** المدير يدخل بكلمة المرور ثم رمز SMS يصل لجواله. إن تعطل الـSMS، فعلى الخادم فقط ضع `ADMIN_LOGIN_OTP=off` في `/etc/jdatna/runtime.env` وأعد تشغيل التطبيق، ثم أزله بعد الإصلاح.

## الطريقة (أ): تجهيز زر الجوال ثم النشر به — موصى بها

1. نفّذ التجهيز لمرة واحدة في `infra/deploy/README.md`:
   - `jdatna-deploy` و`jdatna-deploy-gate` و`jdatna-switch` و`jdatna-migrate` وأمر اختبار الاستعادة `VERIFY_CMD` (إلزامي).
   - حساب النشر المخصص `jdatna-deploy` بلا shell عام ولا Docker، مع sudo مقيد بسكربت النشر وحده.
   - ملف `/etc/jdatna/deploy.env` مع `MIGRATE_CMD`.
   - مفتاح SSH المقيد على حساب `jdatna-deploy` (لا root).
   - بيئة `production` في GitHub بأسرارها الثلاثة.
2. جرّب `jdatna-switch` و`jdatna-migrate` يدويًا مرة: التحويل إلى الإصدار الحالي نفسه، والترحيل على قاعدة `jdatna_test_`.
3. من GitHub: Actions ← «نشر جدتنا (يدوي)» ← `status`. يجب أن يظهر `30b97ec`.
4. ثم `deploy-migrate` واترك الإصدار فارغًا. يوافق المالك على البيئة من الجوال.
5. تحقق من نجاح الخطوة الأخيرة في GitHub، ومن أن `/api/health` يعرض الإصدار الجديد.

بعد ذلك **يصبح النشر مباشرًا:** كل دمج في `codex/jdatna-platform` ينجح فيه CI يُنشر تلقائيًا، ويبقى الزر اليدوي للرجوع أو الحالة. ولا تفعّل Required reviewers في بيئة production إن أردت النشر بلا موافقة يدوية.

## الطريقة (ب): نشر يدوي مرة واحدة (إن لم يُجهَّز الزر)

حسب `docs/START_HERE.md` و`AGENTS.md`:
1. نسخة احتياطية مشفّرة واختبار استعادتها: `systemctl start jdatna-backup.service`.
2. على الخادم، صدّر المصدر من Git مباشرة دون SCP:
   ```sh
   git -C /opt/jdatna/deploy-src fetch origin codex/jdatna-platform
   git -C /opt/jdatna/deploy-src archive <sha> | tar -x -C /opt/jdatna/releases/<sha>
   ```
3. ابنِ الصورة: `docker build --build-arg SOURCE_COMMIT=<sha> -t jdatna-application:<sha> /opt/jdatna/releases/<sha>`.
4. احمِ الصورة بحاوية حارس: بلا شبكة ولا منافذ ولا أسرار.
5. طبّق `017` ثم `018` بحساب **migrator** فقط، وتحقق من صلاحيات `app` على عمود `producer_seen_at` (قراءة وتحديث).
6. حوّل وسم الصورة في Coolify، ثم تحقق من `/api/health` ومن صفحات الرئيسية و`/browse` و`/dashboard/orders`.
7. أزل الحارس، وخذ نسخة بعد النشر، وحدّث `docs/RELEASE.json` والتسليم.

## بعد النشر — فحص سريع

- الرئيسية تعرض «وش طلبك اليوم؟».
- `/browse` يعرض الأزرار الأربعة.
- حساب أسرة تجريبي على قاعدة اختبار فقط، لا الإنتاج: إرسال طلب يُظهر الرسالة المنبثقة خلال 30 ثانية.
- لا SMS ولا حسابات وهمية في الإنتاج.
